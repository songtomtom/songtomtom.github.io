이 시리즈는 한 질문에서 시작했습니다. 코딩 에이전트의 규칙 파일이 두 달 만에 96줄에서 616줄이 된 저장소가 있었고, 거기서 "규칙은 짧게, 절차는 Skill로, 금지는 Hook으로"를 적용하자 같은 작업의 비용이 48% 줄었습니다. 그 경험을 공개 저장소에서 작게 다시 만들며 층마다 쟀습니다. 다섯 편의 결과를 한 자리에 놓습니다.

## 다섯 층, 한 표

| 층 | 무엇을 | 잰 것 | 결과 |
|---|---|---|---|
| [규칙·절차·결정 분리](/blog/coding-agent-harness-rules-skills-decisions) | 123줄 → 29줄 + Skills 4 + decisions 10 | 작업 5개 통과·비용·턴 | 품질 같음, 비용 같음, 턴 +52%. Skill 자동 선택 4/5 |
| [절차형 Skill](/blog/coding-agent-harness-procedural-skill) | 범위→TC→승인→실행→리포트 QA 세션 | 게이트 준수 시나리오 3개 | 없을 때 외부 호스트에 실행 시도, 산출물 0. 있을 때 거부·산출물 3 |
| [Hook](/blog/coding-agent-harness-hooks-bypass) | 쓰기 전 차단 → 변경 줄 검사 + Stop | 검사 횟수·차단·도구 사용 | 쓰기 도구 Hook은 셸 쓰기에 미발동. 결과 검사로 바꿔 1건 차단 |
| [서브에이전트](/blog/coding-agent-harness-subagents) | 읽기 전용 리뷰어, 결정 조회 | 위반 3개 검출·위임 여부 | 정의만으로 미호출. 명시하면 형식 계약 |
| [평가 세트](/blog/coding-agent-harness-evaluation) | 고정 작업 9개 자동 채점 | 층별 비교표 | 품질 층과 무관, 채점기 3회 수정 |

## 효과가 있었던 것

**결과를 검사하는 것.** 이 시리즈에서 실제로 무언가를 막은 장치는 둘뿐입니다. 변경된 줄을 검사하는 Hook(색 값 하나를 토큰으로 바꾸게 했다)과, 외부 호스트를 거부하는 실행 도구. 둘 다 에이전트가 **무엇을 했는가**를 보지 **어떻게 했는가**를 보지 않습니다. 쓰기 도구에 건 검사는 에이전트가 셸로 쓰는 순간 끝났고, 지시문은 에이전트가 안 읽으면 끝났습니다. 결과물과 실행 경로에 둔 검사만 남았습니다.

**절차를 산출물로 강제하는 것.** QA Skill이 바꾼 것은 에이전트의 성실함이 아니라 **남는 것**이었습니다. 없을 때도 테스트는 열심히 했지만 채팅 답변만 남았고, 있을 때는 TC·결과·리포트 파일이 남았습니다. 절차는 "이 순서로 하라"보다 "이 파일들이 있어야 끝난 것이다"로 적을 때 지켜졌습니다.

**측정을 먼저 두는 것.** 평가 세트가 없었다면 "Hook 차단 0건"을 준수로 읽고 끝났을 것입니다. 검사 횟수를 세어 봤기 때문에 미발동을 알았고, 로그를 열어 봤기 때문에 lint가 빠진 것을 알았습니다. 채점기가 세 번 틀린 것도 측정이 있었기에 드러난 것입니다. 하네스의 각 층보다 측정 장치가 먼저여야 합니다.

## 효과가 없었던 것

**작은 저장소에서 규칙 문서 축소는 비용을 줄이지 않았습니다.** 123줄은 매 턴 주입돼도 작고, 분리하면 Skill을 읽는 턴이 늘어납니다. 616줄에서 48%가 줄었던 것은 그 크기였기 때문입니다. 분리는 길이가 어느 선을 넘었을 때의 처방이고, 그 전에는 **구조**를 위한 선택입니다. 결정이 파일 단위로 남고, 절차가 골라 읽히는 것.

**하네스는 이 작업 세트의 품질을 올리지 못했습니다.** 다섯 층 모두 규칙 위반 0, 통과율 차이는 lint 하나. 123줄 한 파일로도 에이전트는 다 지켰습니다. 규칙이 작고 명확하면 하네스 없이도 지켜집니다. 하네스가 필요한 지점은 규칙이 많아져 묻히거나, 사람이 매번 확인할 수 없거나, 어기면 비용이 큰(운영 서버에 실행) 곳입니다. 그 지점을 재려면 더 어려운 작업이 필요하고, 그건 아직입니다.

**정의는 호출을 보장하지 않습니다.** Skill은 대체로 골라 읽혔고, 서브에이전트는 이름을 부르기 전에는 호출되지 않았습니다. 같은 "필요할 때 쓰라"인데 다릅니다. 반드시 거쳐야 하는 경로는 지시문이 아니라 구조로 만들어야 합니다.

## 616줄에서 있었던 일

규칙 문서가 616줄까지 자란 저장소에서 같은 분리를 했을 때는 이 시리즈와 세 가지가 달랐습니다.

첫째, 결정이 40건이었고 번복이 14건이었습니다. "예전엔 이랬는데 이렇게 바꿨다"가 규칙 문장 사이에 괄호로 끼어 있었고, 그것을 파일 52개로 빼내자 규칙 본문이 절반 이하로 줄었습니다. 결정 기록 분리의 효과는 결정 수에 비례합니다.

둘째, 비용이 48% 줄었습니다. 10개 작업에 $4.55가 $2.35가 됐습니다. 매 턴 616줄이 사라진 값입니다.

셋째, 거기서도 품질은 같았습니다. 통과율과 규칙 위반이 전후 동일했고, 에이전트가 셸로 써서 Hook을 우회한 것도 거기서 먼저 발견한 것입니다. 이 시리즈의 3편은 그 발견을 작은 저장소에서 재현한 것입니다.

## 다음에 세운다면

1. **평가 세트부터.** 고정 작업 5개와 자동 채점. 하네스 층은 그 다음입니다. 첫 측정은 "지금 상태"를 재는 것이고, 거기서 무엇이 새는지가 다음 층을 정합니다.
2. **결과 검사를 먼저.** 변경된 줄을 검사하는 Hook(`PostToolUse(Bash)` + `Stop`)을 쓰기 도구 Hook보다 먼저 겁니다. `Stop`에는 typecheck·lint·규칙·관련 테스트를 다 넣습니다. 거기 없는 것은 샙니다.
3. **규칙 문서는 길이가 아니라 종류로 나눕니다.** 항상 지킬 것, 할 때 읽을 것, 왜 그런지. 분량이 작아도 종류가 섞이면 결정이 규칙 사이에 끼기 시작합니다.
4. **반드시 거칠 경로는 구조로.** 리뷰가 꼭 에이전트를 거쳐야 하면 `/review` Skill이 에이전트를 띄우게 합니다. 지시문의 "필요하면 쓰라"는 안 쓰입니다.
5. **안전 규칙은 도구에도.** 외부 호스트 거부처럼 어기면 되돌릴 수 없는 것은 Skill 문장과 실행 도구 양쪽에 둡니다.
6. **채점기를 믿지 않습니다.** 실패 하나하나의 로그를 엽니다. 이 시리즈의 발견 대부분이 거기서 나왔습니다.

## 남은 것

- `Stop` Hook에 lint와 관련 테스트를 넣고 다시 재기. 그러면 모든 층이 9/9가 될 것이고, 그때부터 작업을 어렵게 만들 차례입니다.
- 작업당 3회 이상 돌려 중앙값으로 비교하기. 지금은 한 번씩이라 턴 수 차이를 말할 수 없습니다.
- 서브에이전트의 손익분기. 리뷰 대상이 커질 때 위임이 메인 컨텍스트를 얼마나 아끼는지.
- Hook 로그를 실제 개발에서 주 단위로 쌓아 "어떤 규칙이 얼마나 자주 걸리는지" 보기. 평가 세트는 통제된 측정이고, 이것은 현장 측정입니다.
